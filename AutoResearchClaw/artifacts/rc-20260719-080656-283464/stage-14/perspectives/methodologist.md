## 方法学审计结论

当前实验作为工程 smoke 是合格的：真实预训练 ViT 已接通，梯度、稀疏性、固定容量、AMP 与前后向均经过检查。但作为研究实验尚不合格。最大问题不是分数低，而是比较尚未隔离研究变量：训练预算极短、只有两阶段单次运行、基线预算未对齐、测试集调参风险不明，且核心指标不足以检验“固定容量内容寻址记忆”的长期价值。

## 1. 基线公平性与完整性

### CaRE 比较尚未证明公平

结果没有确认 CaRE 与 basis 方法是否严格共享以下条件：

- 相同预训练 checkpoint；
- 相同数据划分、样本顺序与增强随机数；
- 相同优化器、学习率调度、weight decay 和梯度裁剪；
- 相同 classifier 更新与校准；
- 相同训练步数、早停和 checkpoint 选择规则；
- 相同 adapter 插入层；
- 相同可训练参数量、存储参数量和实际计算预算。

尤其需要区分三种预算：

1. 总存储参数；
2. 每样本激活参数和分析 FLOPs；
3. 实测延迟、吞吐量与显存。

当前 sparse rank-16 与 dense rank-4 只匹配了分析 FLOPs。它们没有匹配存储参数和表达秩，实测延迟也分别为 0.753 ms 与 0.533 ms。稀疏版本慢约 41%，所以“等计算对照”这一标签不充分。

### 缺少机制归因所需的最小基线

严格受 stage-10 范围约束时，不需要扩展到大量外部方法，但以下内部对照不可缺：

- 冻结 ViT＋相同 classifier，无 adapter；
- `scale=0`；
- 参数匹配的单个低秩 adapter；
- 固定或随机 Top-2 路由；
- 只训练 basis、固定路由；
- 只训练路由、固定 basis；
- Hard/Signed/dense 使用相同 rank 的对照；
- Hard/Signed/dense 使用相同存储参数预算的对照。

否则，`scale=0.1` 的提升可能只是减弱了有害 adapter 扰动，不能归因于内容寻址或 basis composition。

### CaRE 之外仍缺一个容量匹配参照

正式阶段至少需要一个固定容量的非内容寻址 adapter bank，才能回答“收益来自固定容量参数本身，还是内容寻址”。如果研究声称优于随任务扩展的方法，还应同时报告参数量随任务数变化的曲线，而非只比较准确率。

## 2. 指标与研究问题的匹配度

### Average accuracy 和 final accuracy 不足以检验核心主张

两阶段下的平均准确率仅为两个评价时点的平均。例如 Hard `scale=0.1` 的 90.055 就是 `(91.22+88.89)/2`。它不能充分描述长期遗忘、容量饱和或路由误差累积。

应增加：

- 每阶段、每旧任务的准确率矩阵；
- BWT；
- 最终旧类准确率；
- 新类即时学习准确率；
- intransigence 或 forward transfer；
- 类别平衡的宏平均准确率；
- calibration error 和类别偏置；
- 多阶段 accuracy–task 曲线及其面积。

### Forgetting 可能奖励欠学习

负载均衡权重 0.1 的 forgetting 为 1.00，但 task-0 准确率只有 88.52；CaRE 的 task-0 为 93.4。初始学得较差的方法本来就可能表现出较小的下降。因此不能将低 forgetting 直接解释为更稳定。

必须同时报告旧类最终准确率、初始峰值、BWT 和新类准确率，明确稳定性是否以可塑性或初始学习为代价。

### 缺少直接测量 memory 和 routing 的指标

研究对象是内容寻址固定容量 memory，但现有科研指标主要测分类结果。还需报告：

- 每槽 usage、路由熵、Gini 系数和 dead-slot 比例；
- Top-2 槽选择在阶段切换前后的变化率；
- 路由对类别、阶段和语义相似性的条件分布；
- basis 有效秩、余弦相似度及冗余；
- adapter 输出相对 backbone residual 的范数；
- 旧样本表征或 prototype drift；
- 容量增加时的准确率—参数 Pareto 曲线。

仅验证“容量固定”是工程属性，并未证明该容量被有效复用。

## 3. 评价协议与泄漏风险

现有材料不足以排除数据泄漏或测试集调参。

需要记录并审计：

- `scale=0.1` 和 balance 权重是依据训练集、验证集还是测试集选定；
- 是否反复查看 CIFAR-100 测试准确率后选择配置；
- checkpoint 是否按测试指标选择；
- classifier prototypes、归一化统计或路由统计是否使用测试样本；
- 第二阶段训练时是否意外访问第一阶段图像、标签或缓存特征；
- 数据缓存是否保持官方 train/test 边界；
- 预处理、resize、augmentation 是否在训练和测试间正确切换；
- 所有方法是否使用相同类别顺序和相同评估代码。

如果 `scale=0.1` 是根据测试表现选择的，该测试集已参与模型选择。正式结果必须使用独立验证方案，或在预先冻结配置后使用未触碰的类别顺序、seed 或数据集进行确认。

ViT-B/16-IN21K 对 CIFAR-100 不构成通常意义上的标签泄漏，但预训练数据重叠和强先验会影响外部有效性。结论应限定为“基于该预训练 backbone 的增量适配”，不能泛化为从头训练或其他预训练来源。

## 4. 消融完整性

当前消融覆盖了路由类型、一个 scale 和两个负载均衡强度，但没有形成因果清晰的因子设计。

至少需要以下矩阵：

### Scale 消融

测试 `0、0.03、0.1、0.3、1.0`，并对 Hard、Signed 和普通 adapter使用相同网格。报告 residual norm，判断改善究竟来自最佳尺度还是 basis 机制。

### 路由消融

在相同 rank、槽数、参数量和输出范数下比较：

- Hard Top-2；
- Signed Top-2；
- dense softmax；
- Top-1；
- 固定均匀组合；
- 随机 Top-2。

### 容量消融

改变槽数和 rank，但分别保持：

- 总参数量固定；
- active FLOPs 固定；
- 实测延迟近似固定。

这三种控制回答不同问题，不能混为一个“公平预算”。

### 均衡消融

除 `0、0.1、1.0` 外，需要更温和的量级，并报告主损失与均衡损失的实际梯度贡献。否则权重数值没有跨实现意义。还应比较全局均衡、容量阈值式惩罚及仅针对 dead slots 的惩罚。

### 阶段切换消融

若计划研究 slot stabilization，应分别控制 key 冻结、路由学习率、basis 学习率和切换窗口长度，避免一次引入多个变化。

## 5. 内部与外部有效性

### 内部有效性：较弱

主要威胁包括：

- 单 seed 和单类别顺序；
- 1 epoch 导致不同方法可能处于不同收敛阶段；
- scale 可能改变优化难度而非最终能力；
- 比较预算未完全匹配；
- 超参数选择协议不明；
- 多个失败或发散配置未系统计入稳定性；
- shared+basis 发散的原因和频率未报告。

当前只能说 `scale=0.1` 在这一次运行中改善了结果，不能确认它是稳定机制。

### 外部有效性：非常有限

50+50 两阶段没有制造真正的固定容量压力，也不能代表目标中的 10、20 或 100-task 长序列。干净任务边界不代表 boundary-free stream；CIFAR-100 也不能代表 ImageNet-R 或 OmniBenchmark-1K。

在长序列、不同类别顺序和 interleaved stream 上验证之前，不能声称该机制解决了路由错误累积、容量非线性增长或跨任务结构复用。

## 6. 可复现性评估

已有日志路径和工程测试是良好起点，但不足以独立复现。

正式实验应保存：

- 代码 commit hash 和未提交 diff；
- 完整配置文件及命令；
- Python、PyTorch、CUDA、驱动和依赖锁定信息；
- GPU 型号、AMP 设置和确定性选项；
- 所有随机 seed，包括数据加载器 worker；
- 类别顺序与 train/validation/test 索引；
- 预训练 checkpoint 的来源及校验和；
- 每个条件的初始化 checkpoint；
- 逐阶段指标、训练曲线及路由统计；
- 全部运行清单，包括失败、发散和被放弃的配置；
- 参数量和 FLOPs 计算脚本；
- 延迟测量的 warm-up、同步、重复次数和误差区间。

Hard 与 Signed 原尺度得到完全相同的 task0/final 数值值得核验：这可能是合理结果，也可能说明配置没有真正生效、日志复用或路由在该设置下退化为相同行为。应检查配置快照、权重统计和实际 signed coefficient 分布。

## 7. 具体改进方案

下一轮应保持 read-only 范围，暂不加入 writer：

1. 冻结方法定义和主要比较，建立独立验证集，停止用测试集选择 scale。
2. 加入 `scale=0`、无 memory 和单 adapter 三个关键内部基线。
3. 采用与正式 CaRE 相同的充分训练步数，记录完整学习曲线。
4. 对 Hard/Signed/CaRE 做至少 3–5 个配对 seed，并覆盖至少 3 个类别顺序。
5. 同时报告均值、标准差、95% 置信区间和配对差值；不要对单次运行做显著性声明。
6. 将 sparse/dense 比较拆成等参数、等分析 FLOPs和等实测延迟三套实验。
7. 输出每阶段旧类/新类准确率以及完整路由与槽利用率诊断。
8. 在配置冻结后扩展至 CIFAR-100 10-task 或 20-task，之后再测试 interleaved stream。
9. 仅当长序列显示固定槽内容本身成为瓶颈时，再进入 bounded writer。

综上，当前方法学足以支持“工程实现通过 smoke 验证”，不足以支持任何机制优越性结论。最优先的工作不是增加模型复杂度，而是建立无测试泄漏、预算对齐、充分训练、配对多 seed 的确认性评价协议。
