- 科学证据质量较低：单 seed、单类别顺序、两阶段、每阶段 1 epoch，没有方差估计，基线预算也未完全匹配。

## Consensus Findings

三个视角的高置信共识如下。

1. **read-only basis memory 已具备可继续研究的工程基础。**  
   现有检查足以排除大量基础实现错误，但不能排除更隐蔽的配置、日志或机制退化问题。

2. **adapter 输出尺度是关键敏感因素。**  
   `scale=0.1` 的大幅改善值得优先复验。现阶段只能说缩小残差提高了这次运行的性能，不能进一步断言它释放了 basis memory 的表达能力。

3. **没有任何核心比较获得统计支持。**  
   Signed 未胜过 Hard；所有 basis 条件仍落后 CaRE；稀疏相对 dense 只有很小的单次准确率差异，而且实际延迟更差。

4. **强全局负载均衡改善槽使用，却明显伤害准确率。**  
   这是可靠的运行内现象，但原因尚不确定。它可能来自专门化与利用率冲突，也可能只是正则过强、欠学习或梯度尺度失配。

5. **现在不应进入 bounded writer。**  
   read-only 机制的基本贡献尚未被隔离。加入写入会同时引入内容更新、覆写冲突和稳定性问题，使归因更加困难。

## Contested Points

### 是否已经形成“方法雏形”

判断：**形成了工程与假设层面的雏形，但没有形成经验证的方法雏形。**

支持继续保留的证据是：真实流程可训练、容量固定、稀疏执行有效，且简单尺度修正使表现明显改善。反对更强表述的证据是：缺少无 adapter、`scale=0` 和普通低秩 adapter 对照，因此无法确认改善来自 memory，而不是“更少扰动强预训练 backbone”。

### Signed 是否有稳定性优势

Signed 在 `scale=0.1` 下 Forgetting 为 2.90，低于 Hard 的 3.22，并略低于 CaRE 的 2.96；但它的 Average 和 Final 也更低。差值来自单次运行，且 forgetting 会受到初始学习水平影响。

结论：**只能视为待检验的稳定性信号，不能称为优势。** 必须比较最终旧类准确率、BWT、新类学习能力和多 seed 配对差值。

### 负载均衡是否揭示了专门化—利用率冲突

balance=0.1 将 Forgetting 降至 1.00，但 Average 从 90.06 降至 87.55。该结果与稳定性—可塑性或专门化—均衡冲突相容，却不是唯一解释。

可能的替代解释包括：

- 正则损失相对主损失过强；
- batch usage 不能代表全局容量利用；
- 均衡迫使路由选择尚未训练好的槽；
- 均衡项改变了残差或梯度幅值；
- 初始准确率降低人为压低 forgetting。

结论：**冲突假说值得测试，但当前尚未被识别为因果机制。**

### sparse 是否优于 dense

当前稀疏 rank-16 与 dense rank-4 只匹配分析 FLOPs，没有匹配存储参数、表达秩或实际延迟。稀疏每层 0.753 ms，dense 为 0.533 ms，稀疏约慢 41%。

结论：**现有比较既不能证明稀疏的准确率优势，也不能证明效率优势。**

## Statistical Checks

当前有效实验单位为一组 seed、类别顺序和训练运行，因此实际样本量为 `n=1`。不能计算有意义的跨运行标准差、置信区间或显著性。

需要重点处理以下问题：

- **随机性未知：** 0.60 点的 Hard–Signed 差异、0.375 点的 sparse–dense 差异和 0.06 点的 Signed–CaRE forgetting 差异，很可能处于正常运行波动范围内。
- **配对条件不明确：** scale 消融是否共享初始化、数据顺序、增强随机数和其他训练随机性没有充分说明。
- **多重比较：** 已经查看多个路由、scale 和 balance 条件。如果根据同一测试集选择 `scale=0.1`，则存在超参数选择偏差和 winner’s curse。
- **报告精度过高：** 在没有不确定性估计时，90.055 不应暗示千分点级分辨率。
- **失败运行选择：** shared+basis 的数值发散必须进入完整运行清单。只报告成功条件会高估方法稳定性。

下一轮应采用至少3–5个配对 seed，并覆盖至少3个固定类别顺序。建议将类别顺序和训练 seed 视为不同变异来源。主要比较应预先指定，报告配对差值、均值、标准差、95%置信区间和实际效应量。探索性超参数搜索与最终确认性实验必须分离。

## Methodology Audit

### 基线公平性

尚未证明 CaRE 与 basis 在以下方面完全一致：

- 预训练 checkpoint；
- 数据与增强顺序；
- optimizer、schedule、weight decay 和梯度裁剪；
- classifier 更新与校准；
- adapter 插入层和训练步数；
- checkpoint 选择规则；
- 总参数、active FLOPs、实测延迟及显存。

至少需要补充以下内部基线：

- 冻结 ViT＋相同 classifier；
- `scale=0`；
- 参数匹配的单个低秩 adapter；
- 固定或随机 Top-2；
- 固定 basis、仅学习路由；
- 固定路由、仅学习 basis。

这些对照用于判断收益究竟来自残差尺度、低秩适配、额外参数、内容寻址还是 basis composition。

### 指标适当性

Average、Final 和 Forgetting 不能完整回答固定容量 memory 是否有效。特别是低初始准确率会压低可观察的 forgetting。

应增加：

- 完整 task-by-task accuracy matrix；
- 旧类最终准确率和新类即时准确率；
- BWT、intransigence及稳定性—可塑性曲线；
- 每槽 usage、路由熵、Gini 和 dead-slot 比例；
- 阶段切换时的槽选择变化率；
- basis 有效秩、相似度和冗余；
- adapter residual norm 与 prototype drift；
- 参数量、吞吐量、延迟和显存。

### 数据泄漏与模型选择

当前材料没有证明发生泄漏，但也不足以排除测试集参与调参。必须确认：

- scale 和 balance 权重是否根据测试结果选择；
- checkpoint 是否按测试准确率选择；
- prototype、归一化或路由统计是否使用测试数据；
- CIFAR-100 官方 train/test 边界是否在缓存中保持；
- 第二阶段是否意外读取旧阶段缓存样本或特征。

如果测试集已经用于选择 `scale=0.1`，它不能继续承担最终确认性评估。应建立独立验证方案，或冻结配置后使用未触碰的 seed、类别顺序和外部数据集确认。

### 消融完整性

建议采用分阶段设计，而不是立即扩大机制：

1. scale：`0、0.03、0.1、0.3、1.0`；
2. 路由：Hard、Signed、dense、Top-1、固定及随机 Top-2；
3. 容量：分别进行等参数、等分析 FLOPs、等实测延迟比较；
4. 均衡：更小权重、dead-slot threshold penalty、容量感知正则；
5. 过渡稳定：分别消融 key 冻结、路由学习率和稳定窗口。

Hard 与 Signed 原尺度得到完全相同的 Task-0 和 Final 数值，需要优先核验配置是否真正生效、日志是否复用，以及 Signed 是否退化成与 Hard 相同的系数行为。

### 可复现性

现有日志路径是良好基础，但完整复现还需要：

- commit hash 和工作区 diff；
- 完整命令与配置快照；
- 依赖、CUDA、驱动和 GPU 信息；
- 所有 seed 与类别顺序；
- checkpoint 来源及校验和；
- 每阶段曲线与路由统计；
- 包括发散在内的全部运行清单；
- 参数/FLOPs 计算方法；
- 延迟测量的 warm-up、CUDA synchronization、重复次数和误差范围。

## Limitations

当前结论受以下边界严格限制：

- 只有 CIFAR-100 的一次 50+50 流；
- 只有两个阶段，无法制造真正的固定容量压力；
- 每阶段1 epoch，无法区分收敛速度与最终能力；
- 没有 boundary-free 或 interleaved stream；
- 没有 ImageNet-R 或长序列验证；
- 没有证明路由选择对应有意义的知识复用；
- 没有证明固定容量优于非内容寻址的同容量参数化；
- 没有实际效率优势，当前稀疏实现反而比 dense 慢；
- 强 IN21K 预训练先验限制了对其他 backbone 或从头训练场景的外推。

因此，当前不能声称解决了长期路由错误、容量饱和、跨任务共享或非线性参数增长问题。

## Conclusion

**建议：REFINE。**

不是 PIVOT，因为实现已经通过关键工程检查，且 `scale=0.1` 提供了足够强的探索性信号，值得继续投入一轮严格验证。也不是直接 PROCEED，因为现有结果没有隔离 memory 的真实贡献，尚不具备进入更复杂 writer 或正式长序列主实验的证据基础。

下一轮的最小决策门应是：

1. 补齐无 adapter、`scale=0` 和单低秩 adapter 对照；
2. 使用与 CaRE 一致的充分训练预算；
3. 对 CaRE、Hard `scale=0.1`、Signed `scale=0.1` 做配对多 seed、多类别顺序；
4. 冻结超参数选择协议并排除测试集调参；
5. 报告旧类/新类分解、BWT、路由和槽利用诊断；
6. 公平匹配 sparse/dense 的参数预算及实测效率。

若 Hard/Signed 在这些检查后仍优于无记忆对照，并在长序列容量压力下保持竞争力，则可正式 PROCEED 到温和防塌缩和 task-transition stabilization。只有确认固定只读槽内容本身成为瓶颈后，才应考虑 bounded writer。
